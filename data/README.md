# UrbanSage AI — External Dataset Integration Guide

Welcome to the data integration hub for **UrbanSage AI**. This directory manages the staging, documentation, transformation, and governance of all external datasets before they are used in environmental intelligence models or ingested into the primary Supabase PostgreSQL database.

---

## Directory Structure

```text
data/
├── raw/         # Original, unmodified datasets manually downloaded or provided
├── processed/   # Cleaned, standardized, and validated datasets generated by transformation pipelines
├── external/    # Supporting spatial shapefiles, ward boundary files, external reference benchmarks
├── metadata/    # Data dictionaries, schema specifications, provenance, and license logs
├── .gitignore   # Git guard rules preventing raw data blobs from entering version control
└── README.md    # Integration instructions, governance rules, and onboarding guide
```

---

## Directory Descriptions & Intended Uses

### 1. `data/raw/` — Ingestion & Staging
- **Purpose**: All newly acquired, downloaded, or exported datasets must be placed directly here.
- **Rules of Engagement**:
  - **IMMUTABLE**: Original files in `data/raw/` must **never** be edited in-place, overwritten, or deleted. They serve as the raw ground truth.
  - **Manual Ingestion**: Simply paste or copy your raw files (e.g. Census metrics, ward spatial geometries, satellite indices, water quality samples, budget ledgers) into this folder.
  - **Potential Formats**: 
    - Tabular: `.csv`, `.tsv`, `.xlsx`, `.parquet`
    - Spatial & Hierarchical: `.json`, `.geojson`, `.gpkg`, `.shp`
    - Scientific arrays: `.nc`, `.h5`
    *(Note: The existence of a format here does not imply the core app already parses it; preprocessing pipelines will convert candidates into standard schemas).*

### 2. `data/processed/` — Pipeline Outputs
- **Purpose**: Cleaned, harmonized, deduplicated, and normalized dataset outputs produced during pipeline execution.
- **Characteristics**:
  - Converted into clean columnar formats (e.g., standard UTF-8 CSV or Parquet).
  - Aligned to UrbanSage AI spatial identifiers (e.g. `neighbourhood_id` matching `NBR-001` through `NBR-010`).
  - Outliers flagged, missing values imputed, or geometries simplified for web rendering.

### 3. `data/external/` — Reference Lookups
- **Purpose**: Auxiliary reference data, lookup tables, and administrative taxonomies.
- **Examples**:
  - Ward code to neighbourhood name mapping dictionaries.
  - Social Vulnerability Index (SVI) baseline tables.
  - Municipal classification tables and standard emissions factor tables.

### 4. `data/metadata/` — Catalog & Provenance
- **Purpose**: Comprehensive documentation for each dataset.
- **Contents**:
  - Data dictionaries describing each column name, data type, unit of measurement, and nullability.
  - Source URLs, publishing agencies, collection dates, and licensing terms (e.g. OGL, Creative Commons, Public Domain).
  - Schema change logs and notes on known data quality anomalies.

## Dataset Ingestion Workflow & Governance

To maintain operational integrity and database health, every dataset follows a strict four-stage gate:

```text
[Step 1: Download] ──> [data/raw/]
                            │
[Step 2: Inspect]   ──> [data/metadata/ (Data Dictionary & Source Log)]
                            │
[Step 3: Transform] ──> [data/processed/ (Normalized schemas & Ward IDs)]
                            │
[Step 4: Approval]  ──> [Review Gate: Schema Compatibility & RLS Verification]
                            │
                       [Supabase / Production Integration]
```

### Critical Rules:
1. **Never import directly to Supabase**: No dataset should be imported into the live Supabase PostgreSQL database or local SQLite until it has been inspected, profiled, validated against application models, and explicitly approved.
2. **Never commit secrets or credentials**: Never place API keys, database connection strings, passwords, or personal PII into dataset files, metadata files, or commit logs.
3. **Preserve data provenance**: For every dataset added to `data/raw/`, create a corresponding markdown descriptor in `data/metadata/<dataset_name>.md` detailing its origin and date.
